# Runbook for Claude Code: validate and finish panbiome-gut-ont

Give this file to Claude Code on a machine that has Docker (or Podman/Singularity) and internet access. Start Claude Code in the unzipped `panbiome-gut-ont` folder and say: "Follow CLAUDE_CODE_RUNBOOK.md, one phase at a time. Stop and report at the end of each phase."

## Context

`panbiome-gut-ont` (v0.1.0) is a Nextflow DSL2 workflow for Oxford Nanopore shotgun gut metagenomes from human stool, laid out for import into the EPI2ME desktop app. It was written without access to Nextflow, so **the Nextflow wiring and the tool command lines have never been run**. The Python helpers in `bin/` and the parameter schema are unit-tested (`python3 -m pytest tests -q`, 8 tests).

Project setting: Panbiome (clinical-grade wellness, bare-minimum clinical validation, not FDA-level). 16 stool samples per PromethION flow cell, washed second use after a human PGx panel, no in-run controls (scheduled control runs instead), 3 to 4 Gb per sample.

## Ground rules

1. Do not claim anything works until you have run it. Report each result as: passed, failed (with the error), or not run (with the reason).
2. Fix the code, not the tests, unless a test is wrong. Say so if you change a test.
3. Do not invent database URLs, container tags, tool flags or Medaka model names. Check them against the tool's own `--help`, `medaka tools list_models`, or its documentation, and record what you verified.
4. Ask before downloading anything larger than 1 GB (databases). Small tool installs and container pulls for the steps below are fine.
5. Keep the placeholder thresholds as they are. Do not tune them; that is validation work done by the lab.
6. Never put real patient data or human reads in the repo or in test data.
7. Keep a running log in `docs/VALIDATION_LOG.md` (date, command, result, what changed).

## Phase 0: Environment

```bash
python3 -m pytest tests -q          # expect 8 passed
docker --version
java -version                       # Java 17 or newer
curl -s https://get.nextflow.io | bash && chmod +x nextflow && ./nextflow -version   # needs 23.10.0 or newer
```

Put `nextflow` on the PATH. Install `nf-core` tools only if you want `nf-core pipelines lint`; they are optional.

## Phase 1: Build the core image

```bash
docker build -t ghcr.io/musicofthings/panbiome-gut-ont-core:0.1.0 -f docker/Dockerfile docker
docker run --rm ghcr.io/musicofthings/panbiome-gut-ont-core:0.1.0 \
  bash -lc 'minimap2 --version; samtools --version | head -1; chopper --version; python -c "import numpy, scipy, pandas, matplotlib; print(\"py ok\")"; ps --version'
```

Check that the image contains `bin/` scripts only if the workflow expects them there (the workflow uses the project `bin/` directory, which Nextflow adds to the PATH). Do not push the image until I say so.

## Phase 2: Stub run (DAG and channel wiring)

```bash
bash tests/stub_run.sh
```

This runs `nextflow run main.nf -stub-run -profile test` against `test_data/` with stub databases. Fix, in order: syntax errors, undefined variables, channel shape mismatches (`join(remainder:true)`, `combine`, optional inputs staged with `stageAs`), missing `emit` names, and output globs that do not match what `stub:` blocks create. Re-run until it finishes. Then confirm that `output/` contains `wf-gut-report.html`, `run/qc_summary.tsv` and one `samples/<alias>/` folder per test sample.

Also run these variants and record whether each completes:

```bash
nextflow run main.nf -stub-run -profile test --assay 16s
nextflow run main.nf -stub-run -profile test --assay both
nextflow run main.nf -stub-run -profile test --skip_assembly
nextflow run main.nf -stub-run -profile test --skip_host_depletion
nextflow run main.nf -stub-run -profile test --control_summary test_data/control_summary.json
```

If a variant needs a file that does not exist, add a small synthetic one to `test_data/` generated by `test_data/make_test_data.py`.

## Phase 3: Real tool check on small data (no large databases yet)

For each tool, confirm the command line in `modules/*.nf` is valid for the pinned container tag in `nextflow.config` (`container_*`). Use `docker run --rm <image> <tool> --help` and compare against the flags used. Tools to check: chopper, minimap2 (`-x map-ont`, `-a`), kraken2, bracken, krona (`ktImportText`), sylph (`sketch` / `profile`, long-read options), emu, flye (`--nano-hq`), medaka (`medaka_consensus` or `medaka inference`; check the model name in `--medaka_model`), semibin2 (`single_easy_bin`, `--environment human_gut`, long-read option), checkm2, gtdbtk, amrfinder (`--plus`, `--database`), genomad (`end-to-end`), pyrodigal (`-p meta`), emapper.py.

Write each finding to `docs/VALIDATION_LOG.md`. Fix wrong flags in the modules. For anything that cannot be verified, add it to a list titled "Unverified" at the top of the log.

## Phase 4: Small end-to-end run with real tools

Build a small public test set so the whole chain runs with real binaries:

1. Pick a small public ONT metagenome or a mock community run (for example a ZymoBIOMICS mock FASTQ from ONT open data or SRA). Subsample to about 200 Mb with `seqtk sample` or `rasusa`. Ask me before downloading if it is over 1 GB.
2. Build tiny databases: a Kraken2 and Bracken database from a handful of genomes, a sylph database from the same genomes, and a minimap2 index of a small decoy "host" genome (not human).
3. Run `nextflow run main.nf -profile standard` with `--skip_binning --skip_assembly` first, then enable assembly, then binning.
4. Confirm the species table, reconcile step and report look sensible for the known mock composition.

Record runtime and peak memory per process from `output/execution/trace.txt`. Update the `label` resource settings in `nextflow.config` if they are clearly too small or too large.

## Phase 5: Full-size databases (ask first)

Follow `docs/DATABASES.md`, checking each command against current documentation before running it. Report expected sizes and ask me before starting any download over 1 GB. Prioritize: T2T-CHM13 host index, GTDB-based Kraken2/Bracken, sylph GTDB database plus the lineage map (`bin/make_sylph_lineage_map.py`), CheckM2, AMRFinderPlus, geNomad, eggNOG. ## Phase 6: Pipeline hygiene

1. Run `python3 scripts/make_schema.py` after any change to `nextflow.config` params, then `python3 -m pytest tests -q`.
2. Run `nextflow config -profile standard` and `nextflow inspect main.nf` (if available) to confirm container references resolve.
3. Optionally run `nf-core pipelines lint` and list findings; do not chase cosmetic ones.
4. Make sure the README "Verification status" table matches reality. Change "Not run" to "Passed on small data" only for things you actually ran, and say with what data.
5. Add a short `CHANGELOG.md` entry for v0.1.1.

## Known assumptions to check first

- sylph options for noisy ONT reads (`--sylph_args`)
- Medaka model name matching the basecaller (`medaka tools list_models`)
- Bracken read length matches the Kraken2 database build (`bracken_read_len`, default 1000)
- Kraken2 and sylph databases share one taxonomy (GTDB), otherwise the reconcile step will not match names
- SemiBin2 long-read mode and the `human_gut` pretrained environment
- Whether `eggnog-mapper` needs its diamond database path passed separately
- Placeholder thresholds (QC, mock community, AMR, watchlist) are unvalidated by design
